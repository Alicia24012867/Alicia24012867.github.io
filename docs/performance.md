## 运行与编译优化

### 列表排序

先为每篇文章解析日期，再排序。日期解析从比较器中的重复操作变成每篇一次；排序本身仍为 O(n log n)，临时日期缓存为 O(n)。置顶优先、时间戳与时区比较、编辑时间回退、同值 slug 排序和输入不可变行为保持一致。标题排序不创建日期缓存。

测量采用相同的 10,000 篇模拟文章，包含置顶、重复标题、不同发布日期和部分编辑日期。每种实现预热三次，然后交替运行 11 轮，取中位数。计时前逐项比较四种排序的完整结果。

| 排序方式 | 重构前（ms） | 重构后（ms） |
| -------- | -----------: | -----------: |
| 最新发布 |       71.719 |       13.535 |
| 最早发布 |       70.513 |       13.084 |
| 最近更新 |       73.473 |       14.374 |
| 标题     |       19.962 |       19.945 |

日期排序在该样本中减少约 80% 的处理时间，标题排序基本不变。当前网站仅有少量文章，实际绝对收益很小；该结果不代表整页加载速度或网络性能。

复现：

```sh
node --experimental-strip-types scripts/benchmark-sort.mjs --compare-ref a1d9dd5
```

不带 `--compare-ref` 时仅测量当前版本。Git 比较需要保留基线提交。

### 内容生成

- 纯文本提取在一次 HTML 清洗中删除脚注引用并展开普通上标，省去第二次完整解析；标题的纯文本不再重复提取。
- 没有附件的正文模块直接导出数据，不再生成空 URL 表或运行无效的替换表达式。
- 正文加载函数表在首次读取文章时才创建，列表浏览无需初始化该表。
- 内容目录为空或缺失时返回空集合并清理旧编译缓存；文件重建后恢复发现、全文搜索与正文加载。

使用同一组 40 篇文本（清理前八篇内容和 32 篇混合语法样例）比较完整编译结果，输出一致。11 轮交替测量中位数约为 166.2 → 162.7 ms，差异较小，因此不据此宣称整体构建有显著加速。

### 文末签名

- 屏外初始状态不创建动画，也不计算关键帧；首次进入视口且页面可见时才初始化。
- 关键帧按需计算并在模块内复用，切换减少动态效果或再次挂载时不用重新计算。
- 动态、减少动态效果和打印共用同一组 16 条墨迹路径，删除重复的静态 SVG 路径。
- 约 6.3 秒完成书写，停留两秒，再严格镜像擦除；约 15.1 秒循环。A/l 的连续曲线与已调整的书写节奏保留。
- 离开视口或切换页签时暂停；减少动态效果时取消动画，通过 CSS 去掉遮罩显示完整签名。

## 第四轮：算法与重复工作

基线提交为 `ad44b7a`，本地测量环境为 Node.js 24.14.0。页面外观、样式与分享卡片像素保持不变，已提交的卡片无需重新生成。

### 静态分享页

- 原实现为每篇文档在整份入口 HTML 上依次执行十余次正则替换，成本约为 O(n·k·S)（n 篇文档、k 个标签、外壳长度 S）。现在每个入口外壳只编译一次：按原顺序逐个定位标签并留下占位，再拆成静态片段；每篇文档只拼接片段与渲染值，成本降为 O(k·S + n·S)。
- 匹配顺序、重复标签只替换第一个、Prettier 换行后的 `<noscript>`、缺少标签时的报错与原实现一致；外壳含 NUL 字符时拒绝编译。缺少分享图仍先于外壳问题报告。
- 开发与预览服务器按 slug 直接查找文档，不再遍历目录。

使用生产构建的 Blog 入口外壳（3,134 字节）渲染 10,000 篇模拟文档，预热三次后交替运行 11 轮取中位数；计时前逐页比较两版输出。

| --------------- | -----------: | -----------: |
| 10,000 个分享页 |        278.5 |         69.8 |

### 目录锚点与脚注

重复标题和同名脚注原先每次从 `-2` 起逐个试探，k 个同名标题共需 O(k²) 次查找。现在为每个基名记住下一个候选后缀，总体为 O(k)。已占用集合只增不减，跳过的后缀不会重新可用，因此结果与逐个试探完全一致；标题自身写明的 id 仍可保留。新增随机序列对照测试，以及 300 个同名标题与碰撞脚注的长例。

### 分享卡片

- 背景裁切与两次半透明叠加每次运行只做一次，各卡片复制同一张底图。
- 标题省略由逐字反复测量整段文字改为累加前缀宽度。Pillow 的字形前进宽度是 1/64 像素的整数倍，累加结果与整段测量相同。
- 本机渲染 9 张卡片（6 张已提交卡片与 3 个省略边界样例）由约 436 ms 降至 255 ms（单次测量，含 Python 启动），JPEG 输出与原渲染器逐字节一致。
- 清理过期卡片时一并删除变空的上级目录；此前多层目录只删除最内层。

### 其他

- `verify-build` 每个文件只读取并压缩一次，入口 HTML 只读取一次；检查与报告结果不变。
- 地址解码统一为 `decodeSlug`，页面路由、内容目录与分享页共用；畸形转义一律视为未找到。
- 开发服务器的订阅、sitemap 与 robots 共用一个响应函数；sitemap、Atom 与分享页共用同一个最后修改时间计算。
- 链接分组与首页锚点列表在模块加载时计算一次，不再在每次渲染时重复过滤。

## 第五轮：内存占用

基线提交为 `74fff98`。页面内存在本机 Chrome 155 无头模式（1280×900）下用生产构建预览测量。外观保持不变：两版构建在 8 个页面上以 1280 px（1×）和 390 px（2×）逐屏截图，另以夜间主题抽查 3 个页面；关闭滚动锚定、冻结动画并屏蔽评论区后，每一屏都与基线截图逐像素一致。同一基线重复截图之间只在手写签名动画的暂停时刻上相差约 10 个像素。

### 字体样式表

- 四个入口原先逐一列出 Noto Sans SC 的 7 个字重和 Playfair Display 的 4 个斜体字重。Google Fonts 为每个字重各返回一整套 unicode-range 分片规则，而这些规则指向同一批 105 个可变字体文件：样式表解码后 797,180 字节（传输约 217 KB），注册 723 个字体。
- 现改为字重区间 `wght@400..700` 与 `ital,wght@1,400..600`：引用的 105 个字体文件完全相同，样式表 115,019 字节（传输约 31 KB），只注册 105 个字体。页面实际用到的字重（正文 400/450/500/600，花体 400/500/550）既在原列表内也在新区间内，可变字体在两种写法下按同一字重取样，字形与排版不变。该样式表会阻塞首次渲染，传输量下降对首屏同样有利。
- 新增测试要求四个入口共用同一字体请求并使用字重区间；README 记录了区间范围，新用的字重需落在区间内。

### 全文搜索

- 原实现第一次搜索时把标题、摘要、标签、分区名与正文拼接后转小写并缓存。正文在构建时已转小写（`searchText`），因此每篇笔记的正文在内存中保留两份。
- 现在只缓存转小写后的元信息；正文转小写后若不变，就继续引用已加载的字符串。匹配依次检查元信息、正文，以及跨越两者之间空格的情况（在查询的每个空格处拆成前后两段），结果与拼接后搜索完全一致。新增测试用所有长度不超过 12 的子串，与拼接方案逐一对照。
- 10,000 篇模拟笔记全部参与一次全文搜索后，保留的堆内存由 13.34 MB 降至 1.57 MB；首次搜索 8.49 → 7.15 ms，14 次热查询 19.04 → 19.25 ms，基本不变。当前只有一篇笔记，实际节省约为其正文大小，并随笔记数量线性增长。

### 其他

- `useMediaQuery` 为每个媒体查询缓存订阅函数和 `MediaQueryList`。原实现每次渲染都生成新的订阅函数，目录高亮随滚动变化时，React 会反复退订、重新订阅并新建 `MediaQueryList`。

## 第六轮：字体自托管

基线提交为 `1a07183`。线上巡检发现每个页面都要先等 Google 字体样式表：它会阻塞首次渲染，而 Google 在中国大陆无法访问，连接被挂起时页面一直空白。在模拟中让 Google 字体服务延迟 10 秒，首次内容绘制从 708 ms 推迟到 10,724 ms；请求被立即拒绝时为 720 ms。

- `npm run fonts:fetch`（`scripts/fonts.mjs`）按原来的请求 `Noto Sans SC:wght@400..700` 与 `Playfair Display:ital,wght@1,400..600` 从 Google Fonts 取回同样的 105 个 WOFF2 文件（4.38 MB，按字符范围切片），放进 `public/fonts/`，并生成同样的 105 条 `@font-face` 规则（`src/styles/fonts.css`，由全站共用的 `global.css` 引入）。四个入口不再连接 `fonts.googleapis.com` 与 `fonts.gstatic.com`，改为预加载两种字体的拉丁字符切片。
- 字体文件与原来逐字节相同，因此外观不变：两版构建在 8 个页面上以 1280 px 与 390 px 逐屏截图（共 77 屏），75 屏逐像素一致；其余 2 屏分别是首页 GitHub 动态的实时文字和手写签名动画的暂停时刻，后者在两次基线截图之间同样不同。
- 屏蔽 Google 后，5 个页面的字体全部从站内加载，无任何 Google 请求。每页仍只下载正文用到的切片：中文文章约 1.0–1.2 MB，与原来相同。
- 规则从 Google 的样式表（解码 115,019 字节，传输约 31 KB）移入站内共用样式表，各入口初始 CSS 的 gzip 增加约 32 KB（首页 9,302 → 41,418 字节），总传输量基本持平，但少连接两个外部域名，并随共用样式表在页面之间缓存。初始 JavaScript 不变。
- 同一标签页内连续浏览时，Chrome 已在内存缓存中保有这两个切片，会在控制台提示预加载未被使用；每次新开浏览器加载任一页面都不会出现该提示。

## 第七轮：正文照片

基线提交为 `1ce184b`。/blog/moments/ 的四张照片一直按原图下载，共 1,106,384 字节，而它们在页面上只有 98–232 px 宽：工资条单独成图（高 360 px），其余三张放在三栏画廊里。

- 构建时 `scripts/content/resize.mjs` 按样式表算出每张照片的显示宽度，为相对路径引用的 JPEG 与静态 PNG 另存副本：像素按宽 430 px 的三倍屏手机和二倍屏电脑所需的较大者再加两成。Chrome 缩小图片超过 2 倍时会改用较模糊的预缩小版本，这两成余量让手机上的缩小倍数保持在 2 倍以下。副本用 sharp 生成（Lanczos3 缩放，JPEG 为 mozjpeg 质量 90），保留原图的色彩配置与色度采样，不含相机信息。
- `srcset` 与 `sizes` 同时列出副本和原图，像素更多的屏幕由浏览器自动选原图；查看器通过 `data-full-src`（或图片外的链接）打开原图。画廊格子是正方形，副本按需缩放；其他照片的高度由文件比例决定，副本取与原图比例完全相同的整像素尺寸（宽高同为最简比的整数倍），所以任何屏幕上的排版都不变。副本节省不足两成，或照片不是 8 位 sRGB 时，仍显示原图。
- 副本按照片内容和目标尺寸命名，缓存在 `node_modules/.vite/article-images/`，替换照片后自动重做。首次构建为这四张照片多花约 0.5 秒，之后复用缓存。
