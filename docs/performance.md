# 性能与验证

## 404 重构（2026-09-21）

- 单页入口平铺为 `src/not-found.tsx`，样式归入 `src/styles/not-found.css`；404 HTTP 测试并入 `tests/plugin.test.mjs`，减少一个目录和一个独立测试文件。
- 导航与布局共用页面类型，布局使用类名映射，昼夜遮罩共用渐变规则。
- 本地 404 中间件以修改时间、元数据变更时间和文件大小判断模板版本，复用读取和转换中的 Promise。并发请求共用一次工作；编辑、重新构建或读取失败后均可刷新，不保留失败的缓存。HEAD 请求跳过正文读取和转换。

在 Node.js 24.14.0 下，将 `ccc9f79` 与本轮中间件用于相同的生产 404 HTML。预热后交替运行 7 轮，每轮连续调用 500 次生产预览中间件并校验 HTTP 状态与响应正文一致。耗时中位数从 **47.168 ms** 降至 **9.090 ms**（约减少 **80.7%**）。这只衡量本地模板处理，不包含网络传输、浏览器渲染，也不代表 GitHub Pages 的性能变化。

HTTP 集成测试覆盖并发与重复请求只读取一次、HEAD 不加载正文、开发编辑与预览重建刷新、同大小文件更新、读取失败重试，以及真实页面和资源仍可访问。404 的图片、三个返回入口、HTTP 404 状态与原地址均保留。

使用相同锁文件在隔离目录构建前后版本，404 初始 JavaScript 与 CSS 的 gzip 合计为 66,455 → 66,480 字节（+25 字节），没有前端包体积下降结论。59 项测试、类型检查、格式检查和生产构建通过；浏览器复查了桌面、320px 窄屏、昼夜主题、菜单 Escape 关闭及返回入口。

## 时间戳重构（2026-09-21）

- Blog 和 Notes 的日期、作者、分区、阅读时长统一由 `src/content/ArticleMeta.tsx` 渲染；删除单独的日期组件和 Blog 元信息组件。
- 日期校验、Git 日期和本地回退集中到 `scripts/content/metadata.mjs`；相关测试并入已有的文章编译和目录测试。相比上一轮未提交的时间戳实现，减少 3 个独立文件。
- 每个仓库版本只扫描一次 Git 历史，Blog/Notes 共用缓存。缓存仅保留最近的仓库与版本，提交变化后重新读取；两个日期均显式填写时不查询 Git。
- 按当前分支第一父提交链记录文章进入该分支和后续修订的时间，合并修改记在合并提交。使用内容对象判断实际修改，重命名及权限变化不会制造编辑日期。

在 Node.js 24.14.0 下，将上一轮工作区快照与本轮实现用于同一临时 Git 仓库：Blog、Notes 各 100 篇文章，两次提交，包含一次正文修订。每种实现交替运行 7 次，每次使用新进程；计时从模块加载完成后开始，比较完整编译结果的摘要确保本次样本输出一致。表中为中位数。

| 阶段 | 重构前（ms） | 重构后（ms） |
| --- | ---: | ---: |
| 首次完整内容构建 | 1487.783 | 98.121 |
| 已有编译缓存的构建 | 16.963 | 17.873 |
| 单篇未提交编辑后的缓存构建 | 17.452 | 18.020 |

该样本的冷构建耗时减少约 93.4%；Git 子进程由 202 次降至 3 次（两次版本查询、一次历史扫描）。缓存构建没有明显改善。本结果仅代表模拟内容编译，不代表页面加载速度，当前 6 篇文章的实际收益更小。

57 项测试覆盖日期覆盖、同日编辑、跨目录移动、多个文件同时重命名、特殊文件名、权限变化、删除后重建、分支合并和 Git 查询次数。日期显示另外通过 Blog/Notes 组件渲染检查。

现有内容基准增加 Git 仓库模式，可复测当前实现：

```sh
node scripts/benchmark-content.mjs --git
```

该命令沿用原有预热流程，主要测量编译缓存；上表冷构建比较则每轮启动新进程，二者计时口径不同。

## 先前的内容路由与搜索优化

本轮于 2026-09-21 使用 Node.js 24.14.0 测量，基线为提交 `aaed459`。历史优化记录可从 Git 历史查看；本页保留当前结构、可复现命令与本轮数据。

## 本轮变化

- Blog/Notes 共用内容路由、页面元信息、正文异步加载和失败状态；三个入口共用站点布局与页脚。
- 内容组件集中在 `src/content/`，阅读器集中在 `src/content/reader/`；首页入口移到 `src/home/main.tsx`。
- 内容索引在一次遍历中建立地址查找与分组；匹配文本在首次非空搜索时整理，每篇只整理一次。浏览列表和直接读正文不做这项工作。
- Notes 等待全文索引期间不再计算不会显示的摘要搜索结果。列表保留分组级缓存，移除每行重复的 `memo` 比较。
- 构建验证与包体积报告合并到 `scripts/verify-build.mjs`，共用依赖图遍历。

## 搜索基准

`benchmark-search.mjs --compare-ref aaed459` 将历史与当前索引实现用于相同的 10,000 篇模拟笔记，每篇含 1,220 个正文字符，4% 的标题包含 `CUDA memory`。两种实现先预热，再交替顺序运行九次，表中为各阶段中位数。计时之外将搜索结果与独立的完整子串匹配结果比较。

| 阶段                     | 重构前（ms） | 重构后（ms） |
| ------------------------ | -----------: | -----------: |
| 列表索引初始化（摘要）   |        1.924 |        0.465 |
| 全文索引初始化           |        4.858 |        0.446 |
| 初始化后的首次全文搜索   |        4.898 |        7.698 |
| 全文初始化 + 首次搜索    |        9.802 |        8.117 |
| 已有缓存的 14 次连续查询 |       21.439 |       21.425 |

列表初始化耗时减少约 76%。文本整理被延迟到首次搜索，因此单看首次过滤会变慢；包含初始化的首次搜索总耗时在本次测量中减少约 17%，后续搜索基本持平。总耗时单独取中位数，不等于两个阶段中位数之和。

连续查询覆盖输入、大小写与空格规范化、删除、替换、无结果和清空。相同规范化查询复用结果，更具体的查询仅过滤上次命中的文章。此基准只衡量同步索引与过滤，不包含下载、React 渲染或浏览器输入延迟。当前站点只有少量示例内容，实际收益远小于万篇模拟数据；绝对耗时随机器负载与垃圾回收变化。
