# R1：第一个接口，第一次部署

目标：`server/` 里有一个能运行的 Rust 程序，回答 `GET /api/health`。推送后，CI 自动测试、构建、检查并部署它，`https://nymphilia.com/api/health` 回答你的版本号。

功能很少，但整条路都要走通：cargo 项目、异步的 Web 服务、Docker 镜像、CI、服务器上的健康检查。以后每个里程碑都沿用这条路。

## 要学的概念

- **cargo 项目：** `Cargo.toml` 写依赖，`Cargo.lock` 记下每个依赖的确切版本（要提交进仓库，CI 用 `--locked` 按它构建），`src/main.rs` 是入口。
- **async / await：** Web 服务同时处理很多请求，大部分时间在等网络。`async fn` 返回一个“将来会完成的任务”（Future），`.await` 等它完成，等待期间线程去做别的事。像 C++20 的协程，但由 tokio 这个运行时负责调度。`#[tokio::main]` 让 `main` 也成为 async 函数。
- **axum 的路由和处理函数：** `Router::new().route("/路径", get(处理函数))`。处理函数是普通的 async 函数，参数是从请求里“提取”的东西（路径参数、查询参数、JSON 正文、共享状态），返回值是能变成响应的东西（`Json<T>`、`StatusCode`、`(StatusCode, Json<T>)` 等）。
- **serde：** 给结构体加上 `#[derive(Serialize)]`，`Json(值)` 就能把它变成 JSON。
- **优雅退出：** 服务器换版本时，Docker 先发 SIGTERM，10 秒后才强行结束。收到 SIGTERM 时，停止接受新连接，处理完手头的请求再退出。
- **多阶段构建：** Dockerfile 的第一阶段用完整的 Rust 工具链编译，第二阶段只放编译好的程序。最终镜像约 15 MB，而不是 1 GB。

## 要做的事

### 1. 建项目

在仓库根目录：

```bash
cargo new server --name blog-api
cd server
cargo add tokio --features full
cargo add axum
cargo add serde --features derive
cargo add serde_json
cargo add tracing tracing-subscriber
```

包名必须是 `blog-api`：Dockerfile 按这个名字找编译出的程序。

### 2. 写 `/api/health`

要求：

- 监听环境变量 `BLOG_LISTEN` 给的地址，没设置时用 `127.0.0.1:8080`。
- `GET /api/health` 回答 `200`，`Content-Type: application/json`，正文：

  ```json
  { "ok": true, "version": "<环境变量 BLOG_VERSION，没有就是 dev>", "features": [] }
  ```

- 启动时用 `tracing` 打一行日志，说明监听的地址和版本。
- 收到 SIGTERM 或 Ctrl-C 时优雅退出。

axum 的写法大致是这样（这是另一个接口，不是答案）：

```rust
use axum::{Json, Router, extract::Path, routing::get};
use serde::Serialize;

#[derive(Serialize)]
struct Greeting {
    message: String,
}

async fn hello(Path(name): Path<String>) -> Json<Greeting> {
    Json(Greeting { message: format!("Hello, {name}") })
}

#[tokio::main]
async fn main() {
    let app = Router::new().route("/hello/{name}", get(hello));
    let listener = tokio::net::TcpListener::bind("127.0.0.1:3000").await.unwrap();
    axum::serve(listener, app).await.unwrap();
}
```

你还需要自己查：

- 怎么读环境变量并给出默认值：`std::env::var` 返回 `Result`；
- 怎么初始化 `tracing_subscriber`，让日志打印出来；
- `axum::serve(...).with_graceful_shutdown(...)` 和 `tokio::signal` 怎么配合。

`unwrap()` 在 R1 里可以先留着，R2 学错误处理时再换掉。

### 3. 写一个测试

在 `main.rs` 末尾加 `#[cfg(test)] mod tests`，直接调用你的处理函数，检查 `ok` 是 `true`、`features` 是空的。用 `cargo test` 运行。CI 每次推送都会跑测试。

### 4. 在本机检查

```bash
cargo run
```

另开一个终端：

```bash
curl -i http://localhost:8080/api/health
npm --prefix web run api:check -- http://localhost:8080
```

接口测试应当显示健康检查一项通过，其余功能因为 `features` 是空的而不检查。

### 5. 加上 Dockerfile

`server/Dockerfile`，照抄即可（已在服务器上试过：镜像约 15 MB，启动 2 秒内通过健康检查）：

```dockerfile
# syntax=docker/dockerfile:1

# Build: Rust on Alpine links one static binary (musl), which runs on a bare Alpine.
FROM rust:1.99.0-alpine3.24 AS build
RUN apk add --no-cache musl-dev
WORKDIR /src
# The dependencies alone first: this layer is built again only when Cargo.toml or Cargo.lock
# change, so most builds compile just your own code.
COPY Cargo.toml Cargo.lock ./
RUN mkdir src && echo 'fn main() {}' > src/main.rs && cargo build --release --locked && rm -rf src
COPY . .
# touch: so cargo sees that main.rs is newer than the stand-in built above.
RUN touch src/main.rs && cargo build --release --locked

# Run: only the binary, certificates for HTTPS, and busybox's wget for the health check.
FROM alpine:3.24.3
RUN apk add --no-cache ca-certificates
COPY --from=build /src/target/release/blog-api /usr/local/bin/blog-api
# The commit being built, which /api/health answers with.
ARG VERSION=dev
ENV BLOG_VERSION=$VERSION BLOG_LISTEN=0.0.0.0:8080
USER 1000:1000
EXPOSE 8080
# The server starts a new image, then waits for this to pass before it counts as live.
HEALTHCHECK --interval=30s --timeout=3s --start-period=10s --start-interval=1s --retries=3 \
  CMD wget -qO /dev/null http://127.0.0.1:8080/api/health || exit 1
CMD ["blog-api"]
```

再加 `server/.dockerignore`，只有一行 `target/`，免得把几百 MB 的编译产物发给 Docker。

几点说明：

- **`HEALTHCHECK` 不能删。** 服务器靠它判断新版本是否正常，没有它的镜像会被拒绝。
- **容器里监听 `0.0.0.0`。** 只监听 `127.0.0.1` 的话，健康检查能通过，Caddy 却连不上。Dockerfile 已经这样设置了。
- **依赖 OpenSSL 的库在 musl 上很难编译。** 选用带 `rustls` 功能的版本，例如 reqwest 的 `rustls-tls`。

### 6. 推送，看它上线

提交 `server/` 的全部文件，包括 `Cargo.lock`，然后推送 `main`。在 GitHub 的 Actions 页面看 **Deploy the blog API**：

1. Test：`cargo test`
2. Build the image
3. Start the image as the server runs it：只读、uid 1000，等健康检查通过
4. Check the API against the contract
5. Publish to the server：交给服务器，健康才上线

第一次构建要编译全部依赖，需要几分钟；之后有缓存，快得多。

上线后检查：

```bash
curl https://nymphilia.com/api/health
ssh nyc /srv/site/bin/activate blog-api
```

第一条应回答你这次提交的版本号；第二条列出服务器上保留的版本，`*` 是在线的那个。域名还没指向服务器时，第一条改用：

```bash
curl -k --resolve nymphilia.com:443:107.170.11.167 https://nymphilia.com/api/health
```

## 常见的坑

- **CI 里 `cargo test` 说 lock file 需要更新：** 改了 `Cargo.toml` 却没有提交新的 `Cargo.lock`。本机运行一次 `cargo build`，再提交。
- **构建时报 `linking with cc failed`：** 某个依赖要编译 C 代码，缺少头文件。先看是哪个库，通常换成纯 Rust 的功能选项就好。
- **健康检查一直不通过：** 在服务器上运行 `docker logs blog-api`。常见原因：程序启动就退出了（看日志里的 panic），或者监听了别的端口。
- **上线后又退回旧版：** 这是自动回滚在保护你。Actions 那一步的输出会说明容器的状态，原因在服务器的 `docker logs blog-api` 里。
